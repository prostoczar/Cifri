# Cifri — full application audit, 14 August 2026

Branch audited: `react-rewrite` at `fe79fab`, working tree clean.
Nothing in the app was changed by this audit. Every finding below is a diagnosis, not a fix.

This ran alongside an active push-notifications session, so no file that session was likely to
touch was edited. All audit tooling was written to a scratch directory outside the repo and is
not committed — the numbers below are reproducible from the descriptions, but the throwaway
scripts themselves were not worth adding to a repo that already has ten check scripts.

---

## The short version

The **engine is in good shape**. Every existing check passes, the anti-cheat rules do what they
claim, and the database is genuinely locked down — anonymous attackers are refused at the grant
level, which is stronger than the RLS the design was relying on. The two security fixes from
earlier sessions both still hold, and I verified them by attacking them rather than by reading
the comments.

Three things are actually wrong, and one of them is a design-level problem rather than a bug:

1. **The difficulty tiers are ordered backwards.** Playing Hard scores roughly *half* what
   playing Easy scores, for the same player. The multipliers under-compensate for the fact that
   harder questions take longer, so a score-maximising player should never touch Hard. This is
   the most important finding in the report.
2. **The Braining result screen shows a scale that disagrees with the score it just gave you.**
   Four of its eight rows state the wrong brain age, one row displays an age no player can ever
   earn, and five of the twelve real ages highlight nothing at all.
3. **About twenty user-facing strings never reach the translation table**, so Russian players see
   English in the middle of the game — including the whole Braining result screen. The i18n key
   parity check is perfectly clean (321/321) and completely fails to catch this, which is what
   made it invisible.

Everything is laid out below, with a prioritised list at the end and an explicit list of what I
could not verify without your input or a real device.

## Phase 2 — security

### Anonymous attacker vs every table: clean, and stronger than expected

All seven tables — `profiles`, `player_state`, `question_attempts`, `daily_results`,
`question_sets`, `verified_daily_results`, `braining_boosts` — refuse select, insert, update and
delete from an unauthenticated client holding only the public anon key.

Every refusal came back as `permission denied for table X`, which means the request never reached
RLS at all: the `anon` role holds no table grants whatsoever. That is a stronger position than
the design documents claim, and it is the right one.

One methodological note, because it changes how much the result is worth. My first pass "passed"
several inserts on PostgREST schema-cache errors — *"could not find the 'user_id' column"* — which
is the payload being wrong, not the database refusing. That is a pass for the wrong reason, and an
audit that accepts it would report PASS on a table anyone could write to. I re-ran every insert
with correctly-shaped payloads built from the real column names in the migrations. All seven still
refused, on permission.

Edge Functions called with no token: `issue-question-set` 401, `submit-attempt` 401,
`delete-account` 401, `login-with-username` 401 `invalid_credentials`. All refuse before doing work.

### The auth-token-in-URL fix: holds

I attacked `scrubUrl` with every shape Supabase actually produces — implicit-flow tokens in the
hash, PKCE `code` in the query, `token_hash`+`type` confirmation links, the legacy `?token=`, both
shapes on one URL at once, and a malformed URL. No secret survives any of them. `utm_*` campaign
parameters are correctly preserved, so the filter is not simply nuking the query string.

I also traced posthog-js 1.415.4 to check that no URL-bearing property escapes the
`/url|referrer/i` key filter, since that regex is what decides which properties get scrubbed at all:

- `get_initial_props()` **flattens** the stored `$initial_person_info` into `$initial_current_url`
  and `$initial_referrer`. Both match the filter, both are flat strings inside `$set_once`, and
  the scrubber recurses into `$set_once`. Covered.
- The keys that *do* escape the filter carry nothing sensitive: `$initial_referring_domain` and
  `$initial_host` are hostnames, `$initial_pathname` is a path, and this app has no routing.
- `safe_merge()` **would** dump the raw un-flattened `{r, u}` object into properties, bypassing the
  scrubber entirely — but it is defined and never called in this build. I verified the identifier
  appears exactly once in `dist/main.js`. This is worth re-checking on any posthog-js upgrade,
  because it is the one path that would reopen the hole silently.

Hardening only, not a bug: `scrubUrlProperties` recurses into `$set` and `$set_once` and nothing
else, so a URL nested under some future differently-named object key would be missed. PostHog also
offers a native `disable_capture_url_hashes` option that is not set; `before_send` is strictly
stronger, so this would be belt-and-braces.

### The keypad-digit-leak fix: holds

`ph-no-capture` is present on all three keypads (Challenge, Braining, Trick) and all six account
screens (Create, Login, Reset, Edit, Forgot, and the reset-password screen).

The important part is that I confirmed *how* PostHog honours it, rather than assuming. In
posthog-js the check walks the tree: `Us(t)` climbs `parentNode` up to `body` and bails if any
ancestor carries `ph-no-capture` or `ph-sensitive`. So marking the keypad container really does
cover every digit button inside it. The Practice tab has no keypad — it uses chip selectors — so
there is nothing to leak there.

### NEW: how good a result can a cheat record while staying completely unflagged?

`check-anticheat.mjs` proves the impossible is rejected, and its own header honestly concedes that
a solver bot reading questions off the screen cannot be stopped. That concession is fair. But it
leaves the number that actually matters unmeasured.

`verified_daily_results.suspect_count` exists so a future leaderboard can decline to rank a
suspicious day. So the question is not "can a bot play" — it is **"what can a bot record with
`suspect_count` still at zero"**, because that is the score that will look exactly like honest play.

I measured it against the real validator, generator and scorer.

**Challenge — a bot reaches the theoretical maximum, unflagged:**

| Questions | Claimed play | Wall clock | Score | Verdict |
|---|---|---|---|---|
| 40 | 15.6s | 16.1s | 810 | **accepted, no flags** |
| 60 | 23.4s | 23.9s | 1227 | **accepted, no flags** |
| 80 | 31.3s | 31.8s | **1633** | **accepted, no flags** |

1633 is the ceiling — all 80 questions in the set, every one correct, every one inside the
2-second window where the speed curve pays its maximum 10 points.

The reason this gets through is precise and worth stating: **the 60-second mode limit is enforced
against the play time the client *claims*, not against how many questions a minute can hold.** A
bot claiming 390ms per answer fits all 80 questions into 31 seconds of "play", which is comfortably
inside the 60-second bound, and nothing anywhere asks why a run that did not exhaust the clock is
reporting half a minute of it. Answer times are kept just above `FAST_ANSWER_FLOOR_MS` (250ms) and
spread enough to clear the uniformity check, and both flags stay silent.

For contrast, a genuine 60-second sweep of all 80 questions at 750ms each scores the same 1633 —
so the bot gains nothing per question. Its entire advantage is *reaching question 80 at all*, which
Phase 3 shows a real player never does: realistic play answers about 9 questions on Hard.

The rate limit allows 200 Challenge sets per day and a day scores as the average of its runs, so a
bot can hold a 1633 average indefinitely.

**Braining — a 20-second trial earns the best possible brain age, unflagged:**

| Per-answer time | Claimed | Brain age | Verdict |
|---|---|---|---|
| 100ms | 12s | 20 | accepted, flagged `inhuman_answer_speed` |
| 260ms | 20s | **20** | **accepted, no flags** |
| 1000ms | 57s | **20** | **accepted, no flags** |
| 4000ms | 207s | 22 | accepted, no flags |

Real players take 2.5–10 minutes. The claimed-time-against-wall-clock check does work — you must
genuinely wait out the time you claim — but the floor is `50 answers × ABSOLUTE_FLOOR_MS`, which is
five seconds, and 20 seconds of waiting is nothing. The same run also earns the 5% Challenge boost.

**How much does this matter?** It does not affect honest players today, and there is no leaderboard
yet, so nothing is currently being corrupted. But `suspect_count` is the mechanism intended to make
a leaderboard safe, and against the most likely real cheat it reads zero. That is worth knowing
*before* the leaderboard is built, not after.

The cheapest partial fix, if you want one: require that a Challenge run which did not exhaust the
set claims a play time close to the full 60 seconds. A run answering 80 questions in 31 seconds is
claiming to have finished the set with half the clock unused, which the client cannot actually do.

### The Braining boost: solid

Server-side accounting is correct. `braining_boosts` is keyed `(user_id, day)` so only one boost
can exist per day, and it is consumed by a single atomic `UPDATE … .is('consumed_at', null)` — the
client is never asked whether it has a boost, and a second attempt updates zero rows. Score-based
achievements read `rawScore`, which `check:achievements-verified` already proves the boost cannot
buy.

### Achievements: local by design, worth stating plainly

Achievements are computed client-side and synced into `player_state`, which is the player's own
mirror and is client-writable by design. So a modified client can grant itself any achievement.
That is not a flaw — the rewards are avatar icons and symbols, nothing is ranked, and making them
server-authoritative would break the offline-first rule for no gain. It is only worth writing down
so that nobody later builds a leaderboard *on* achievement counts without realising.

## Phase 3 — difficulty and balance, via simulated play

### How to read this section

The **scoring is real** — every simulated run is marked by the shipped `scoreAttempt()` against
sets from the shipped generator. The **player is modelled**, because there is no telemetry from
real players yet. How long a human takes over `94 − (125 ÷ 25) + (−42)` is an assumption.

So:

- **Relative comparisons between tiers are robust** — all three tiers run through the same model.
- **Absolute scores depend on the calibration**, which is anchored on the single data point in
  `generator.js`: *"the fastest recorded play is around 40"* questions in sixty seconds.
- I ran a **sensitivity pass** shifting the whole speed model ±25%. The headline conclusion does
  not move, and I say which conclusions do.

### What each tier actually asks — model-free

Sampled 160,000 questions per tier from the real generator. No assumptions in this table at all.

| | Easy | Medium | Hard |
|---|---|---|---|
| 1-digit operand | 6.4% | 2.8% | 0.0% |
| 2-digit | 93.6% | 57.2% | 21.0% |
| 3-digit | 0.0% | 40.0% | **79.0%** |
| 2 terms | 100% | 60.2% | 46.7% |
| 3 terms | 0% | 39.8% | 26.5% |
| 4 terms | 0% | 0% | 26.8% |
| negative operand shown | 0% | 18.3% | 27.6% |
| decimal in the question | 0% | 0% | **50.4%** |
| negative answer | 0% | 18.1% | 24.5% |
| **non-integer answer** | 0% | 0% | **68.5%** |
| median \|answer\| | 27 | 80 | 255 |
| points per correct answer | 12.20 | 16.27 | 20.05 |

The escalation is clean and deliberate: Easy→Medium introduces 3-digit operands, a third term and
negatives; Medium→Hard introduces a fourth term and decimals. Nobody would confuse the three.

Two things worth flagging. **Hard makes 68.5% of its answers non-integer** — two questions in three
require typing a decimal point. I checked, and every Hard answer is at most one decimal place
(0 dp: 75,406; 1 dp: 164,594 out of 240,000), so there is no repeating-decimal nightmare. But it is
a lot of keypad work, and it is a large part of why Hard is slow.

Braining has no tiers: an even 25% split across the four operations (no percentage), 75.5% 2-digit,
a 50/50 split of 2 and 3 terms, no decimals, no negative operands, 5.4% negative answers, median
answer 19. It is materially easier per-question than Challenge-Easy; its difficulty is its length.

### THE HEADLINE: the tiers are ordered backwards

Ratio of median score to the tier below:

| Profile | medium/easy | hard/medium | **hard/easy** |
|---|---|---|---|
| perfect play | 0.94× | 0.83× | **0.78×** |
| realistic play | 0.84× | 0.67× | **0.56×** |
| error-prone | 0.73× | 0.53× | **0.39×** |

**Playing Hard costs you roughly half your score.** A player who cares about their number should
play Easy forever, and the worse a player is, the more punishing the harder tiers become — which
is exactly backwards from what a training app wants.

This survives the model being wrong. Shifting the whole speed model ±25%:

| speed shift | easy | medium | hard | hard/easy |
|---|---|---|---|---|
| 25% faster | 257 | 223 | 162 | 0.63× |
| as modelled | 178 | 147 | 99 | 0.56× |
| 25% slower | 130 | 103 | 63 | 0.48× |

Hard never gets close to parity under any calibration.

**Why.** A tier has to make up for asking fewer questions in the same sixty seconds, and the
multipliers do not:

| Tier | questions/run | vs easy | `DIFF_MULT` | needed just to break even |
|---|---|---|---|---|
| easy | 18.4 | 1.00× | 1.00 | 1.00 |
| medium | 13.1 | 0.71× | 1.30 | ≈1.40 |
| hard | 9.2 | 0.50× | 1.60 | **≈2.00** |

Hard asks half as many questions as Easy, so it needs roughly double the per-question value merely
to break even — and it is given 1.6×. The true figure is higher still than 2.00, because accuracy
also falls on Hard (87.7% vs 91.4%) and every wrong answer is a flat −2.

**What would fix it.** I re-scored one fixed pool of simulated play under candidate multipliers, so
the only thing changing is the multiplier:

- **Option A — every tier worth the same** (difficulty becomes pure preference):
  `easy 1.00, medium 1.58, hard 2.83` → medians 178 / 178 / 177.
- **Option B — harder tiers pay about 15% more per step** (rewards the risk):
  `easy 1.00, medium 1.81, hard 3.74` → medians 178 / 204 / 235.

I would recommend **Option B**. Option A removes the penalty but leaves no reason to ever move up;
Option B gives a player a reason to graduate, which is what a training app is for. Either way this
is your call, not mine — it is a design decision about what the tiers are *for*, and the numbers
above are just what each choice costs.

**Caveat I want to be honest about:** these multipliers are only as good as the timing model. The
*direction* of the fix is certain (Hard is badly under-rewarded, and by roughly a factor of two).
The *exact* figures should be re-derived from real telemetry once you have it — you now collect
per-question attempt data, so this becomes a measurement rather than a model within weeks of launch.

### Do the tiers overlap?

Share of runs a tier scores below the median of the tier below it:

| Profile | medium below easy-median | hard below medium-median |
|---|---|---|
| perfect play | 76.6% | 95.7% |
| realistic play | 80.3% | 93.1% |
| error-prone | 82.9% | 89.5% |

The tiers are statistically very distinct. They are just distinct in the wrong direction.

### Is 60 seconds the right window?

Two measures, both ratios, so neither depends on the calibration.

**Spread** — one player, same skill, repeated runs. Wide spread means the score is measuring the
question draw rather than the player:

| Tier | questions | p10 | p50 | p90 | (p90−p10)/p50 |
|---|---|---|---|---|---|
| easy | 18 | 142 | 178 | 212 | **39%** |
| medium | 13 | 109 | 148 | 189 | **54%** |
| hard | 9 | 61 | 99 | 143 | **83%** |

**Signal** — two genuinely different players, independent question sets and independent luck (the
realistic case; a paired comparison flatters this badly and I discarded my first version of it):

| Tier | 5% better player wins | 10% better | 25% better |
|---|---|---|---|
| easy | 63.5% | 76.3% | 97.8% |
| medium | 60.4% | 71.8% | 95.1% |
| hard | 59.2% | 68.7% | 91.5% |

**My opinion: 60 seconds is right for Easy and Medium, and thin for Hard.** Nine questions is a
small sample, and Hard's day-to-day score is twice as noisy as Easy's in relative terms. For a
daily game that is defensible — variance is part of the fun, and the streak and the daily average
smooth it out. It would *not* be defensible as the basis of a competitive leaderboard, where a
single Hard day is close to a coin-flip between players of similar ability.

What a longer window would buy (spread; lower is better):

| Tier | 30s | 60s | 90s | 120s | 180s |
|---|---|---|---|---|---|
| easy | 56% | 39% | 31% | 27% | 22% |
| medium | 78% | 54% | 44% | 38% | 31% |
| hard | 121% | 83% | 66% | 57% | 46% |

Note that `CHALLENGE_SET_SIZE` is 80, so a window long enough to exhaust the set would need the set
enlarged too — a longer window is not free. I would **not** change the window. Fixing the tier
multipliers is the higher-value change, and it is the one that will make players willing to play
Hard at all.

### Braining — simulated times and ages

| Profile | mean | p10 | p50 | p90 | brain age p10 / p50 / p90 |
|---|---|---|---|---|---|
| perfect play | 72s | 67s | 72s | 77s | 20 / 20 / 20 |
| realistic play | 181s | 167s | 180s | 195s | 20 / 20 / 22 |
| error-prone | 291s | 266s | 290s | 317s | 28 / 32 / 36 |

**Braining's scale bottoms out for most players.** The first band is "anything up to 180 seconds →
age 20", and realistic simulated play sits right on that boundary at 180s. A player who improves
from 180 seconds to 72 seconds — a genuinely large improvement — sees their brain age not move at
all. The top of the scale (ages 46–80) needs six minutes or more, which only the error-prone
profile approaches.

So the scale is compressed at the good end and stretched at the bad end. If Braining is meant to
show improvement over time, most players will hit the floor early and then see a flat line. Worth
considering a finer bottom band (say sub-90s, sub-120s, sub-150s) once you have real timing data.

### BUG: the displayed brain-age scale disagrees with the brain age it gives you

This is a straightforward defect, not a balance opinion.

`BR_SCALE` in `supabase/functions/_shared/braining.js` computes the age — 12 bands. `BR_SCALE_SHOWN`
in `src/store/braining.js` is what the result screen draws — 8 bands. They do not agree.

| Displayed row | claims age | brAge() actually gives | agrees? |
|---|---|---|---|
| Under 3 min | 20 | 20 | yes |
| 3 – 4 min | 25 | **22, 25** | **no** |
| 4 – 5 min | 32 | **28, 32** | **no** |
| 5 – 6 min | 40 | **36, 40** | **no** |
| 6 – 7 min | 46 | 46 | yes |
| 7 – 9 min | 57 | **53, 62** | **no** |
| 9 – 10 min | 72 | 72 | yes |
| Over 10 min | 80 | 80 | yes |

Consequences:

- Ages **22, 28, 36, 53 and 62** are reachable but appear nowhere on the displayed scale. The
  result screen highlights the current row with `age === s.age`
  (`BrainingResultScreen.jsx:78`), so a player landing on any of these sees **no row highlighted
  at all**. That is 5 of 12 bands, covering about 30% of the plausible time range.
- Age **57** is displayed but can never be earned by anyone.
- A player finishing in 3m05s is told their brain age is 22 while the scale in front of them says
  "3 – 4 min → 25".

Since brain age is written into `verified_daily_results` as a competitive value, the computed
scale (`BR_SCALE`) is the one that is right and the displayed one should be regenerated from it.
It is a small fix but it touches a user-facing screen, so it belongs in its own session.

I also measured `posthog-js/dist/module.slim.js`: 790.04 kB raw / **231.89 kB** gzipped, saving
about 37 kB gzipped — roughly half of PostHog's cost. **But I do not recommend it without runtime
testing.** The slim build only *references* the `autocapture` and `web_vitals` config keys far
fewer times than the full build (6 vs 22, and 2 vs 14), which strongly suggests it accepts those
options without implementing them. This app uses both. A silently-disabled autocapture would be
worse than the 37 kB.

**The recommendation I am confident in is lazy-loading.** `initAnalytics()` is called from
`src/main.jsx` before the first render, deliberately, so the load pageview is not lost. Moving to
`const posthog = (await import('posthog-js')).default` after first paint would take all 78 kB off
the critical path without losing a single feature. The tradeoff is honest and small: the initial
`$pageview` would fire a few hundred milliseconds later, and a player who bounced inside that window
would go unrecorded. Given that the alternative is 78 kB on the critical path of every cold load on
a phone, that seems clearly worth it — but it is a real tradeoff and it is your call.
